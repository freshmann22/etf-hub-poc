2. 200개 결과를 어떻게 해석해야 하나

블라인드 리뷰는 ground truth가 아닙니다. 동일 taxonomy와 제공된 동일 근거로 분류가 재현되는지 보는 독립 모델 1차 심사입니다. 외부 사실 확인을 금지했으므로 실제 상품 진실성 검증보다 규칙·정의·근거의 일관성을 측정합니다.

유효한 신호

  • 반복 이견이 정의·규칙의 빈틈을 드러냄
  • 근거가 약한 facet을 우선순위화
  • 캐시·재개·합본의 운영 가능성 검증

과대해석 금지

  • 65.5%를 전체 정확도로 외삽 금지

  • 단일 모델·단일 패스 결과

사람 검수 우선

4. 병렬 실행 권장안

권장: 3 workers × batch 10

5개보다 3개부터 시작

  • 배치 10은 20회 모두 5분 timeout 안에 성공
  • 현재 협업 슬롯은 루트 포함 4개라 worker 최대 3개
  • 동일 OAuth quota를 공유하므로 5개 동시는 429·throttle 위험 증가
  • 배치 15~20은 출력·timeout 실패 시 재작업 손실이 커짐

5. 병렬화 전에 반드시 고칠 것

입력

전수 manifest

현재 표본 생성기는 200개로 고정입니다. 1,141개 코드 순서, taxonomy·model·prompt·schema 버전을 고정한 immutable manifest가 필요합니다.

쓰기 충돌

worker와 merge 분리

현재 여러 worker가 공용 합본 JSON·CSV·HTML을 덮어쓸 수 있습니다. worker는 batch 파일만 쓰고, 마지막 단일 merge 단계가 전수 결과를 한 번만 생성해야 합니다.

복구

retry와 원자적 저장

429·5xx·network·timeout에 exponential backoff와 jitter를 적용하고, 임시 파일 검증 후 atomic rename으로 성공 결과를 확정해야 합니다.

  • 파일명에 범위와 코드 hash 포함: batch-000200-000209-<hash>.json
  • promptHash에 정확한 model ID, schemaVersion, runnerVersion 포함
  • batch range gap/overlap 0, 전수 unique code 1,141, taxonomy 고아 tag 0 검증
  • summary 수치를 rows에서 다시 계산해 JSON·CSV·HTML 간 일치 확인

6. 권장 실행 게이트

  1. G0 — 기준 고정: 현재 200 결과를 보존하고 69개 이견을 정책·규칙·데이터 문제로 분류합니다.
  2. G1 — runner 보강: 전수 manifest, run-id, worker-only, merge-only, retry, atomic write를 구현합니다.
  3. G2 — 30개 병렬 smoke: 3 workers가 각 배치 하나씩 실행해 429·timeout·덮어쓰기 0을 확인합니다.
  4. G3 — 잔여 C 270: 50~100개 wave로 처리하고 readiness별 이견·근거 부족 추세가 악화되지 않는지 봅니다.
  5. G4 — D 671: 데이터 보강 전에는 provisional/candidate로 유지하고, 보강 후 전수 리뷰합니다.
  6. G5 — 독립 QA: facet·등급·희소태그 층화 표본에 대해 사람 기준 precision/recall/F1과 재실행 Jaccard를 확인합니다.
